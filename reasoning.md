# Linha de raciocínio

> **Arco.** Exploramos inicialmente os dois datasets do desafio (GitSkills e SpecMine) e escopamos o estudo em **SpecMine**, que reúne 17 ferramentas de *spec-driven development*, das quais ficamos com a **OpenSpec** (58,4% das specs), a única com a marcação "tarefa concluída" verificada contra um commit-âncora: a pergunta de rastreabilidade (spec→código, tarefas marcadas como concluídas mas sem código no commit) era a mais nova e apoiada pelo dado; o GitSkills ficou fora do escopo. Migramos do sample para o dataset completo e vimos, no censo (a população completa), que 10,3% das 332.168 tasks concluídas têm código ausente no commit-âncora, e que o gap se concentra na change ativa (17,7% vs 9,0% na change arquivada: taxas por grupo, cada uma sobre o próprio denominador, não parcelas dos 10,3%), ainda que, em números absolutos, a maioria dos ausentes (73,5%) esteja nas arquivadas, o grupo muito maior. Classificando essas referências, mostramos que 91% dessas 34.227 são arquivos reais (não ruído de path), que, na amostra M8, ao classificar por desfecho (`never`, `deleted_before_anchor`, `created_later`, `renamed`, `other`) as 1.298 referências dos repositórios clonados com sucesso, 84% se mostraram genuinamente ausentes (54,5% `never` + 29,5% `deleted_before_anchor`), que a composição dos resultados também varia entre as faixas de estrelas, e que, na amostra M8, repositórios com requisitos de acessibilidade apresentaram proporção agregada de `never` maior (60,4% vs 41,5%) e mediana por repositório também maior (70,7% vs 50,0%), mas sem evidência estatística para rejeitar a hipótese nula (Mann–Whitney U bilateral, p = 0,169), ficando como observação descritiva a investigar.

### Premissas

Um esclarecimento sobre a fonte dos dados, que vale para todo o estudo: a maioria das análises utiliza artefatos pré-minerados do SpecMine, como os arquivos Parquet. O M6 também processa o conteúdo textual bruto de `specs.jsonl` para identificar requisitos de acessibilidade. Já o M8 é a única etapa que vai além dos artefatos fornecidos para clonar repositórios e reconstruir a classificação dos arquivos por meio do histórico Git.

Um esclarecimento de escopo, que vale para todo o estudo: o SpecMine não é uma única ferramenta. Ele reúne artefatos de **17 ferramentas** de *spec-driven development* (mais o Kiro, em um censo separado) e de quatro "path buckets" sem ferramenta identificada. Dentre elas, ficamos com a **OpenSpec** (58,4% das specs) porque é a única cujo formato traz a marcação de tarefa concluída verificada contra um commit-âncora; as demais têm documentos de requisitos, design e tarefas, mas não esse par. Isso restringe todo o estudo ao OpenSpec, e estender a pergunta às outras 16 ferramentas fica como trabalho futuro.

A direção do estudo veio de uma exploração inicial do modelo de dados: a tabela `openspec_code_refs` já traz `task_done`, `exists_at_anchor`, `anchor_sha` e `resolved_path`, que são as colunas exatas para perguntar "a task marcada como feita tem código no commit?", e é isso que torna a rastreabilidade (Q1) respondível diretamente a partir dos campos do dataset, sem necessidade de inferência estatística (M2).

O `reproduction-steps.md` é o *como*: a receita passo-a-passo (M0–M8) para reproduzir cada resultado. Cada M# daqui corresponde ao mesmo M# lá.

### Vocabulário (para quem não é desenvolvedor)

- **acessibilidade (accessibility)**: exigências que uma spec declara para que o software seja utilizável por pessoas com deficiência (leitores de tela, contraste, navegação por teclado). No estudo, "repositório com requisitos de acessibilidade" é aquele cujas specs mencionam essas exigências. *(desenvolvido em M6, retomada em M8)*
- **alternative_path (caminho alternativo)**: desfecho em que o mesmo nome de arquivo aparece em outro caminho do repositório (0 casos no estudo). *(desenvolvido em M8)*
- **amostragem estratificada / estrato**: dividir a população em grupos (estratos) *antes* do sorteio, para garantir que cada grupo apareça na amostra. No M8, os estratos são a combinação de faixa de estrelas e linguagem. *(desenvolvido em M8)*
- **âncora / commit-âncora** (`anchor_sha`): o commit específico (o "retrato" do repositório) contra o qual o SpecMine verificou se o arquivo apontado pela ref existia. "Código ausente no commit-âncora" = naquele retrato exato, o arquivo não está lá. Quando a âncora é `NULL`, não há retrato para conferir, e a pergunta "existe?" fica sem resposta. *(desenvolvido em M3/M4)*
- **archived (change arquivada)**: uma spec de uma mudança *já concluída* do OpenSpec (vive em `changes/archive/`). Não é "abandonada": o gap "done but missing" é *menor* aqui (9,0%). *(desenvolvido em M3)*
- **bare filename** (`bare_ext`): um `code_path` com só o nome + extensão (ex.: `foo.ts`), sem diretório. É um arquivo real, mas não diz *onde* ele deveria estar. *(desenvolvido em M5)*
- **bilateral (teste)**: um teste estatístico que considera diferenças "nos dois sentidos" (o grupo A ser maior *ou* menor que o B). O oposto, "unilateral", só olha para um sentido. *(desenvolvido em M8)*
- **branch**: uma linha paralela de desenvolvimento dentro do mesmo repositório.
- **camada**: cada tabela/arquivo do dataset representa um tipo de informação (a camada das specs, a camada dos pull requests, a camada das referências). "Camada" é sinônimo de "tabela de um certo tipo de dado".
- **cauda longa / assimétrico à direita**: o formato comum em dados de software: poucos itens gigantes e muitos minúsculos, o que "puxa" a média para cima e faz a distribuição pender para a direita (assimétrica), em vez de uma curva simétrica (normal). *(desenvolvido em M0)*
- **censo**: olhar para a **população inteira** (todos os casos), em vez de uma amostra. As etapas M3 a M7 são censo; o M8 é a amostra. *(desenvolvido em M3)*
- **change_proposal (change ativa)**: uma mudança *ainda ativa* do OpenSpec (vive em `changes/<nome>/`), cujas tasks podem estar marcadas como feitas no documento sem o código ainda ter aterrissado. É onde o gap se concentra (17,7%). *(desenvolvido em M3)*
- **clean path** (`relative_ext`): um `code_path` com diretório + extensão (ex.: `src/foo.ts`), que aponta para um lugar exato e dá para verificar direto. *(desenvolvido em M5)*
- **clone (clonar, `git clone`)**: baixar uma cópia completa de um repositório (com todo o histórico) do GitHub para o computador local, para poder reconstruir o que aconteceu com cada arquivo. *(desenvolvido em M8)*
- **code_path**: a coluna de `openspec_code_refs` que guarda o caminho de código que uma task *nomeia* no `tasks.md` (a spec cita "esta tarefa é implementada em `src/foo.ts`"). É a própria spec dizendo *onde* o código deveria estar; não vem de um commit. *(desenvolvido em M5)*
- **commit**: um "retrato" salvo do código num dado momento; cada mudança fica gravada como um commit com data e autor.
- **concluída (done)**: uma tarefa cujo checkbox foi marcado como feito pelo autor da spec (`task_done=1`). Atenção: "concluída" aqui significa *marcada como concluída na spec*, e o estudo todo pergunta exatamente se essa marcação corresponde a código que realmente existe.
- **created_later (criado depois)**: desfecho em que o arquivo apontado pela ref só aparece em um commit **depois** do âncora: o código chegou atrasado ("lag" de implementação), mas chegou. *(desenvolvido em M8)*
- **dataset**: o conjunto de dados (as tabelas) fornecido pelo desafio, no formato Parquet.
- **deleted_before_anchor (escrito-e-removido)**: desfecho em que o arquivo de código apontado pela ref foi criado, mas apagado antes do commit-âncora. *(desenvolvido em M8)*
- **estatística descritiva / inferencial**: *descritiva* resume o que se observou (médias, porcentagens, medianas) sem afirmar causa; *inferencial* tenta generalizar da amostra para a população e exige um teste com hipótese nula e p-value. O M8 descreve medianas (descritivo) e testa a hipótese com Mann–Whitney U (inferencial). *(desenvolvido em M8)*
- **estrelas (stars) / maturidade**: a contagem de estrelas do GitHub de um repositório (`repo_stars`), usada como *proxy* de "maturidade": mais estrelas ≈ repo estabelecido/sério; poucas ou nenhuma ≈ experimento/abandonado. Estrelas medem popularidade, não maturidade de engenharia; é uma convenção, não uma medida direta. *(desenvolvido em M8)*
- **exists_at_anchor**: uma coluna de `openspec_code_refs` que diz se o código apontado pela tarefa *existe* no commit de referência (`1` presente · `0` ausente · `2` ambíguo · `NULL` âncora ausente). *(desenvolvido em M3)*
- **força-push (force-push)**: reescrever o histórico Git à força, apagando ou alterando commits antigos; pode fazer uma âncora sumir no clone. *(desenvolvido em M8)*
- **Git**: o sistema de controle de versão que guarda, em cada repositório, o histórico de mudanças: cada alteração salva vira um "commit".
- **hipótese nula (H0) / hipótese alternativa (H1)**: a convenção dos testes estatísticos: a H0 é a posição cética ("não há diferença entre os grupos"), e a H1 é "há diferença". O teste tenta reunir evidência *contra* a H0; se não consegue, "não rejeitamos a H0". *(desenvolvido em M8)*
- **is_merged**: uma coluna de `pull_requests` que diz se o PR foi *fundido* (aceito e incorporado ao código). No dataset todos os 5.992 PRs têm `is_merged=1`, então os rejeitados ficam invisíveis. *(desenvolvido em M2)*
- **living (viva)**: a spec *atual* do OpenSpec (`specs/<capabilidade>/`). Não tem `tasks.md`, logo não gera refs "done but missing". *(desenvolvido em M3)*
- **Mann–Whitney U**: um teste estatístico que compara dois grupos (ex.: repositórios com vs. sem acessibilidade) sem exigir que os dados sigam a curva normal. Responde se as taxas dos dois grupos parecem vir da mesma população. *(desenvolvido em M8)*
- **média / mediana / skew (assimetria)**: três resumos de uma distribuição. **Média** = soma dividida pelo total (o "normal", sensível a valores gigantes). **Mediana** = o valor do meio (metade acima, metade abaixo; imune aos gigantes, descreve o típico). **Skew** = o quanto a distribuição pende para um lado (0 = simétrico; além de ±1 = já bem assimétrico). *(desenvolvido em M0)*
- **never (nunca)**: desfecho em que o arquivo de código apontado pela ref jamais foi criado no histórico do repositório, em nenhuma branch. *(desenvolvido em M8)*
- **non_file (não-arquivo)**: um `code_path` que não aponta para um único arquivo verificável: um padrão de busca com curinga ("glob", ex.: `src/*.ts`), um caminho absoluto, ou um nome sem extensão. Conta como "ruído" na taxonomia. *(desenvolvido em M5)*
- **OpenSpec**: o sistema (fluxo de trabalho, "workflow") de especificação que o SpecMine minera: as specs vivem em `changes/` (propostas ativas), `changes/archive/` (concluídas) e `specs/` (atuais).
- **other (outro)**: desfecho que não se encaixa nas demais categorias: âncora ausente no clone (por força-push) ou situação ambígua. *(desenvolvido em M8)*
- **papel de ciclo de vida** (`spec_role`): a categoria de cada spec segundo a fase em que está no workflow do OpenSpec: change arquivada, change ativa, ou viva. *(desenvolvido em M3)*
- **Parquet**: um formato de arquivo colunar e compactado usado para guardar as tabelas do dataset.
- **pull request (PR)**: um pedido de mudança de código que alguém propõe e que passa por revisão antes de ser aceito ("fundido") no repositório.
- **p-value (valor-p)**: a probabilidade de se observar uma diferença tão grande (ou maior) quanto a encontrada, **se a hipótese nula fosse verdadeira**. p baixo (abaixo do nível de significância) = evidência contra a H0; p alto (como o 0,169 do M8) = sem evidência suficiente. *(desenvolvido em M8)*
- **ref (referência)**: o elo que liga uma tarefa da spec ao arquivo de código que deveria implementá-la. "Contar refs" = contar esses elos spec→código. É a unidade central de contagem do estudo.
- **renamed (renomeado)**: desfecho em que o arquivo apontado pela ref existe, mas sob outro nome (o Git rastreia a renomeação). *(desenvolvido em M8)*
- **repositório (repo)**: a pasta de um projeto no GitHub com todo o seu código e histórico.
- **ruído de path**: um "falso ausente": o caso em que o código até existe, mas o caminho do arquivo foi escrito de forma estranha/inválida. "Não é ruído de path" = a ausência é real, não é um caminho mal escrito. *(desenvolvido em M5)*
- **sample (amostra)**: uma fatia pequena do dataset completo, usada para explorar rapidamente antes de olhar tudo. Não é o dado inteiro; é um recorte.
- **significância (nível de)**: o limiar combinado (geralmente 5%, ou seja, p < 0,05) abaixo do qual a evidência é considerada forte o bastante para rejeitar a hipótese nula. *(desenvolvido em M8)*
- **spec (especificação)**: um documento em linguagem natural (Markdown) que descreve o que o software *deve fazer*. É o "pedido" escrito antes do código. No SpecMine, cada spec pode trazer uma lista de tarefas (`tasks.md`) com checkboxes.
- **task (tarefa)**: um item de trabalho descrito na spec, listado no arquivo `tasks.md` com um checkbox. O estudo conta essas tarefas e pergunta se as concluídas correspondem a código real.
- **task_done**: uma coluna de `openspec_code_refs` que marca, para cada tarefa, se ela foi *concluída* no `tasks.md` (`task_done=1` = marcada como feita). É o critério por trás de "concluída (done)".
- **taxa de "missing"**: a proporção `exists_at_anchor=0 ÷ total de refs concluídas com âncora`. É a medida do M3 (10,3%) e **não** é a mesma coisa que a taxa de "never" (uma sub-classificação feita depois, no M8). *(desenvolvido em M3)*
- **taxa de "never"**: a proporção `never ÷ total de refs`. "Taxa de never 54,5%" = de cada 100 refs "done but missing", ~54 apontam para código nunca escrito.
- **verificável (verifiable)**: um requisito de acessibilidade que dá para conferir objetivamente: tem um verbo obrigatório ("deve"/"shall"/"must") ou um limiar mensurável (um número, uma razão, um nível AA/AAA de acessibilidade web). *(desenvolvido em M6)*

> Um **glossário técnico** (definições formais dos campos como `done but missing`, `exists_at_anchor`, etc.) está no fim deste documento.

### Por onde começamos?

Antes de inferir qualquer coisa, precisamos descrever o *formato* do dado, ou seja, o que ele parece. A pergunta de abertura não é "qual é a resposta?", mas "como é a matéria-prima com que vamos trabalhar?". Essa matéria-prima é o recorte **OpenSpec** do SpecMine (58,4% das specs), a única das 17 ferramentas com marcação de tarefa concluída. Para isso escolhemos uma única medida: o tamanho de cada spec em linhas (`n_lines`). Por que essa e não outra?

Primeiro, porque tamanho é a medida mais *primitiva* que existe. Toda spec tem um comprimento, e ele não depende de nenhuma decisão nossa; não precisa parsear, não precisa interpretar. Qualquer outra informação (número de tópicos, de blocos de código, de palavras-chave) é uma *feature derivada*, que já carrega uma hipótese do pesquisador sobre o que importa. `n_lines` é o ponto de partida neutro.

Segundo, porque é de graça: a coluna já vem pré-computada no dataset, então é a escolha mais barata, e barato aqui também é virtude, pois evita introduzir erro de processamento.

Terceiro, e mais importante, porque tamanho é o *canário na mina*. Em todo corpus de software, distribuições de tamanho (linhas de código, tamanho de arquivo, tamanho de spec) são famosamente de cauda longa: poucos itens gigantes, muitos minúsculos. Se queremos caracterizar a distribuição deste corpus (se ela é aproximadamente simétrica ou apresenta cauda longa), `n_lines` oferece um ponto de partida simples. Essa caracterização ajuda a compreender a variável analisada, mas não determina automaticamente os procedimentos estatísticos das demais etapas. A escolha de cada método depende da variável, da unidade de análise, do desenho amostral e das hipóteses específicas do procedimento.

Há ainda um elo com o que vem depois: a análise adiante compara *contagens* (requisitos de acessibilidade por repositório, referências por repositório), e essas contagens também têm cauda longa. `n_lines` é, na prática, uma contagem de tamanho, um representante honesto dessa família de variáveis.

Uma honestidade importante: `n_lines` não é a variável da hipótese central do estudo (a hipótese central é sobre a *taxa* de código ausente, uma proporção). Ele foi escolhido como o *representante canônico de uma variável quantitativa de contagem*: aquele que nos diz, logo de cara, "este corpus é fortemente assimétrico à direita, com cauda longa, então não assuma normalidade". É uma pergunta de *saneamento*, não de hipótese.

E por que não outra coisa? Qualquer feature derivada exigiria parsing e já embutiria uma decisão; qualquer variável categórica (como `archived`) não serve para medir a *forma* de uma distribuição, pois skew e Shapiro-Wilk só fazem sentido em variável quantitativa. Na verdade, o M0 fica só com `n_lines`, a variável quantitativa para a *forma*. O lado categórico (a *composição* do corpus, via `spec_role`) só entra mais adiante, no M3, onde ele de fato cruza com o fenômeno do estudo.

## M0: Sample stats (SpecMine)

1. **Pergunta:** como é o dado do SpecMine (sample)?
2. **Dado de origem:** SpecMine sample (v1.1): `spec_content_features.n_lines` e `spec_files.spec_tool` (composição por ferramenta).
3. **Código/critério:** `m0_sample_stats.py`: média/mediana/skew (sobre o sample completo) + Shapiro-Wilk (subsample de 5.000, limite do teste). O gráfico vem de `chart_m0.py`, que aplica um corte no 99º percentil **apenas para visualização**; as estatísticas reportadas aqui vêm de `m0_sample_stats.py`, sobre os dados **sem corte**.
4. **Resultado:** `n_lines` média 90,8, mediana 56, skew 11,4, Shapiro p≈0. Composição por `spec_tool`: `openspec` 77,4% (22.132 de 28.583 specs), `speckit` 6,5%, `docs_embedded` 5,2%, `specweave` 3,4%, `moai` 2,3%, `specs_generic` 1,7%; as outras 15 categorias somam menos de 1% cada.
5. **Análise e Interpretação:** Antes da forma do dado, uma nota de composição que vale para todo o estudo: o sample é **77,4% OpenSpec**, e isso é proposital. Entre as 17 ferramentas do SpecMine, a OpenSpec é a única cujo formato traz a marcação de tarefa concluída (`task_done`) verificada contra um commit-âncora (`anchor_sha`/`exists_at_anchor`); as demais têm documentos de requisitos, design e tarefas, mas não esse par. É por isso que o estudo inteiro se apoia nas specs OpenSpec. Voltando à forma, começamos pelo sinal mais barato que existe: comparar **média e mediana juntas**. Na distribuição normal, que é simétrica e unimodal, as três medidas centrais (média, mediana e moda) coincidem. Neste estudo, a diferença entre média e mediana é um primeiro indício de assimetria, posteriormente complementado pela skew e pelo teste Shapiro–Wilk. Aqui não coincidem: a média de `n_lines` (90,8) é bem maior que a mediana (56,0). A leitura é imediata: poucas specs *gigantes* puxam a média para cima, enquanto a mediana, imune a esses outliers, fica perto do valor típico. Reportamos as duas de propósito: a **mediana descreve o valor típico**, e a **média revela a influência dos gigantes**. A média é sensível a extremos e a mediana não, e é mostrar as duas juntas que expõe essa diferença. Para **quantificar** essa inclinação, calculamos a **skew (assimetria)**, que mede se a distribuição pende para um lado. A regra prática: skew ≈ 0 é simétrico; valores além de ±1 já são fortemente assimétricos. O valor obtido (**11,4**) é extremo, confirmando uma cauda longa à direita. Em seguida veio o teste formal, o **Shapiro-Wilk**, que testa a hipótese nula "os dados vêm de uma distribuição normal". O p-value, reportado como aproximadamente zero devido ao arredondamento, fornece evidência estatística muito forte contra a hipótese de normalidade; isso não significa que a probabilidade de H0 ser verdadeira seja aproximadamente zero. Além disso, com uma subamostra de 5.000 observações, o Shapiro–Wilk pode detectar desvios pequenos da normalidade; por isso, a interpretação considera conjuntamente o histograma, a assimetria e as estatísticas descritivas. Uma ressalva importante: nunca *provamos* a não-normalidade; apenas **rejeitamos a normalidade**. (O Shapiro-Wilk tem baixo poder estatístico para detectar desvios em amostras pequenas, mas isso não se aplica aqui: o corpus é grande (28.583 specs), e o teste é aplicado a uma subamostra de 5.000.) Sobre o subsample de 5.000: a análise utiliza uma subamostra de 5.000 observações para o Shapiro–Wilk e calcula o skew nessa mesma subamostra, garantindo consistência entre os indicadores. A escolha de 5.000 não deve ser descrita como um limite rígido da função `scipy.stats.shapiro`: a documentação do SciPy alerta que, acima desse tamanho, o p-value pode não ser preciso, embora a estatística W continue precisa. Dois pontos a favor: 5.000 é uma amostra enorme, então a estimativa é estável; e o sorteio usa `random_state=0` (seed fixa), então **qualquer pessoa que re-rodar obtém exatamente o mesmo resultado**, o princípio de reprodutibilidade. Estruturamos tudo como uma **escada de evidência**, do sinal mais simples ao teste mais formal: *média vs. mediana* (há indício de assimetria?) → *skew* (quão forte?) → *Shapiro-Wilk* (podemos rejeitar a normalidade formalmente?). Analisando o gráfico, percebemos que **três indicadores diagnósticos complementares convergem para a mesma interpretação**: (1) média ≫ mediana, indício de cauda longa à direita; (2) skew = 11,4, assimetria extrema; (3) Shapiro-Wilk p ≈ 0, rejeição formal da normalidade. Nenhuma medida isolada bastaria, mas as três juntas contam a mesma história; é essa convergência que torna a conclusão robusta. Podemos então dizer que o dado é **fortemente assimétrico à direita, com cauda longa**: a maioria das specs é curta (mediana 56 linhas), mas existem algumas specs de *milhares* de linhas, e essas poucas gigantes criam uma cauda direita longa e grossa. Ou seja, há **evidência fortíssima de que a distribuição de `n_lines` não é normal e é fortemente assimétrica à direita**. Uma nota sobre o gráfico que acompanha este marco, porque ele pode induzir a uma leitura errada. Como a cauda é extrema, o histograma corta os valores no 99º percentil (`n_lines.clip(upper=552)`); sem esse corte, os 286 specs mais longos esmagariam o corpo da distribuição e todos os 60 bins ficariam visualmente perto de zero, escondendo o formato do grosso dos dados. O efeito colateral é uma barra isolada na ponta do eixo, que parece um pequeno segundo pico perto de 550 linhas. Ela não é um agrupamento real de specs em torno de 550 linhas: é a cauda comprimida num único bin. O top 1% (286 specs, de 552 até o máximo de 6.610 linhas) foi saturado em 552 e caiu todo no último bin, que por isso concentra 298 specs (286 saturados mais 12 que já pertenciam àquela faixa), contra 8 a 13 nos bins vizinhos, um salto de cerca de 30×. Sem o corte, esses 286 valores se espalhariam de 552 a 6.610 numa cauda finíssima e o pico desapareceria. A barra é, portanto, a assinatura visual dos "gigantes" que puxam a média para 90,8 enquanto a mediana fica em 56; não um segundo modo da distribuição. A consequência prática é mais modesta, e mais honesta, do que "abandonar testes paramétricos". Dois fatos mudam o peso da descoberta. Primeiro, o estudo não ajusta modelos de regressão linear. Portanto, pressupostos como linearidade, homocedasticidade e independência dos resíduos não são requisitos aplicáveis aos procedimentos executados. Os testes estatísticos utilizados têm finalidades específicas: Shapiro–Wilk no M0, para avaliar a normalidade de `n_lines`, e Mann–Whitney U no M8, para a comparação exploratória das taxas por repositório. Segundo, os resultados centrais são **censos**, não estimativas de amostra: o 10,3% do M3 conta sobre as 332.168 refs *todas*, e a taxonomia do M5 sobre os 34.227 *todos*; não há incerteza amostral para um teste de significância resolver. Onde há amostragem de fato, no M8, reportamos proporções descritivas da amostra e uma checagem inferencial exploratória no nível de repositório. Esta última não incorpora os pesos do desenho amostral e, portanto, não estabelece por si só uma relação populacional. A pergunta "paramétrico ou não-paramétrico?" **não se decide aqui**: o M0 é essencialmente **descritivo**. A checagem inferencial da hipótese substantiva do estudo (o Mann–Whitney U do M8, aplicado às taxas por repositório) foi escolhida em função da variável analisada, da unidade de análise e do desenho amostral, não da distribuição de `n_lines`. O Shapiro–Wilk permanece como teste específico de normalidade de `n_lines`, com finalidade diagnóstica. O valor real do M0 é, então, **descritivo**: saber que `n_lines` é assimétrica orienta *como resumir e apresentar*: usar a mediana como medida típica, reportar a média com a ressalva da cauda, e nunca tratar a média como "o valor típico".
6. **Decisão + alternativas:** Não estabelecer uma regra estatística universal com base na distribuição de `n_lines`. A escolha de cada procedimento deve considerar a variável, a unidade de análise, o desenho amostral e as hipóteses do método.
7. **Significado:** o dado é *fortemente assimétrico à direita, com cauda longa*; dá o contexto e justifica as escolhas estatísticas de toda a análise.
8. **Ligação:** mostrou que precisávamos escolher **uma** pergunta específica e ver se o sample era representativo (M1).

## M1: Sample vs Full: o sample é representativo?

1. **Pergunta:** o sample difere muito do dataset completo?
2. **Dado:** SpecMine sample (v1.1) vs full (v1.0): `spec_files`, `openspec_code_refs`, `spec_links`, `pull_requests`, e `spec_content_features.n_lines` (para o skew do OpenSpec-only).
3. **Código/critério:** `m1_sample_full.py`: contagem de linhas por tabela; composição por `spec_tool`; média/mediana/skew + Shapiro-Wilk de `n_lines` só para OpenSpec.
4. **Resultado:** sample 28.583 specs = 6,1% dos 470.795; refs 7,0%; a camada PR é 5.335 (89% dos 5.992); a composição também diverge: 51,5% `archived` no sample vs 33,3% no full. Composição por `spec_tool` no full: `openspec` 58,4% (274.955 de 470.795), `speckit` 11,6%, `adhoc_other` 8,2%, `specs_generic` 6,7%, `docs_embedded` 4,1%, `root_bare` 3,7%, `caffeine` 3,0%, `conductor` 1,6%, demais <0,5% cada. No sample, o OpenSpec sobe para 77,4% (super-representado). OpenSpec-only (`n_lines`, n = 273.953): média 77,8, mediana 52,0, skew 15,4, Shapiro p≈0.
5. **Análise e Interpretação:** A pergunta parece simples ("o sample é parecido com o full?"), mas ela decide a validade de tudo o que vem depois. Antes de confiar em qualquer número do sample, precisávamos saber se ele é um *retrato em miniatura* do dataset (como uma amostra aleatória bem feita) ou um *recorte enviesado* (como fotos escolhidas a dedo). A forma mais barata de testar é comparar contagens simples: specs, refs, PRs. Se o sample fosse representativo, todas cairiam na **mesma** proporção (≈ o tamanho da fatia); não caem, e é essa *diferença entre proporções* que conta a história. O tamanho bruto não assusta: 28.583 specs é **6,1%** das 470.795 do full, e uma fatia de 6% *pode* ser representativa se for sorteada ao acaso. O problema aparece na composição interna: a camada de PRs tem 5.335 registros no sample (**89%** dos 5.992 do full), ou seja, quase completa em PRs mas rala em specs. Essa discrepância é a assinatura de uma amostragem *não-aleatória*: uma camada foi quase toda incluída, a outra só uma fração; o sample não é um microcosmo, é um recorte que preserva uma camada e afina outra. O achado decisivo está na composição por `spec_role`: no full, **33,3%** das specs são `archived`; no sample, **51,5%**: o sample *sobre-representa as arquivadas*. Por que isso importa tanto? Porque, como o M3 vai mostrar, a taxa de "done but missing" **não é uniforme** entre papéis: é baixa nas changes arquivadas (9,0%) e alta nas changes ativas (17,7%). Um sample com excesso de arquivadas iria *subestimar* o fenômeno que queremos medir; medir a taxa no sample seria medir no lugar errado, num recorte inclinado para a categoria de *menor* gap. Um reforço em favor do OpenSpec: o skew de `n_lines` só das specs OpenSpec no full é **15,4** (média 77,8, mediana 52,0, Shapiro p≈0), ainda mais assimétrico que o sample geral (11,4), confirmando que a cauda longa do M0 vale exatamente para o subconjunto que vamos analisar. A conclusão é um comando, não um número: **migrar para o full**. O censo do M3 precisa da população inteira, não de uma fatia enviesada de 6%. O sample cumpriu seu papel (foi a bancada de exploração barata), mas qualquer headline sobre "quantas tasks concluídas não têm código" tem de ser calculado no dataset completo.
6. **Decisão + alternativas:** migrar para o **full**: o sample é uma fatia star-curated pequena demais para o censo.
7. **Significado:** o fenômeno precisa ser medido no full, não no sample.
8. **Ligação:** levou à migração do sample para o **dataset completo** (M3).

## M2: O pivô de pesquisa

1. **Pergunta:** qual é a pergunta real que o dado sustenta?
2. **Dado de origem:** (não é dado; é decisão) leitura do call do desafio + os dois preprints.
3. **Código/critério:** não se aplica (é uma decisão conceitual).
4. **Resultado:** a **rastreabilidade (Q1)** vira o núcleo; a **acessibilidade (Q2)** vira secundária; a **revisão de PRs (Q3)** é rebaixada a ameaça; **confiança** vira motivação, nunca conclusão causal.
5. **Análise e Interpretação:** O M2 não produz um número: produz uma **decisão**, e é a decisão mais cara do estudo, porque ela descarta duas perguntas inteiras. O ponto de partida é uma assimetria que não aparece à primeira vista: as três perguntas não têm o mesmo *peso de evidência*. A pergunta de rastreabilidade (Q1) foi praticamente *feita sob medida* para o SpecMine: a tabela `openspec_code_refs` já vem com as duas colunas que a pergunta exige (`task_done`, que marca o que foi concluído, e `exists_at_anchor`, que marca se o código existe). Ou seja, o dado responde Q1 **por construção**, sem que a gente precise inferir nada. Já a pergunta de revisão de PRs (Q3) tem o problema oposto: ela exige ver *rejeição* (o PR que um humano olhou e recusou), e é exatamente isso que o dataset não guarda. Os 5.992 PRs que tocam specs estão **todos** com `is_merged=1`: só os aprovados e fundidos estão lá. Os rejeitados e fechados (onde a desconfiança apareceria) são **invisíveis**. Isso é um viés de sobrevivência clássico: olhar só para o que "sobreviveu" (foi aceito) e tirar conclusão sobre o que foi descartado, como avaliar a qualidade de uma receita olhando apenas os pratos que saíram da cozinha, nunca os que voltaram para trás. Não é que Q3 seja desinteressante: é que ela é **irrespondível** com este dado: qualquer resposta seria inventada, não medida. O mesmo cuidado se aplica à palavra "confiança". A tentação é concluir "specs revisadas geram mais confiança no código", mas confiança não é algo que o dataset mede; ela entra no estudo como **motivação** (o porquê de nos importarmos com o gap), e nunca como conclusão causal. A acessibilidade (Q2), por fim, fica como pergunta **secundária**: ela é respondível (o M6 conta os requisitos verificáveis), mas não é o eixo do SpecMine. A escolha de Q1 como núcleo é, portanto, menos uma preferência do que um **encaixe**: é a única das três em que a pergunta e o dado se alinham sem sobra nem falta.
6. **Decisão + alternativas:** Q1 como central porque o SpecMine foi *desenhado* para isso (`openspec_code_refs` já traz `task_done` + `exists_at_anchor`); Q3 descartada porque todos os PRs do dataset têm `is_merged=1` (os rejeitados/fechados, onde a desconfiança apareceria, estão invisíveis).
7. **Significado:** esta decisão molda todos os passos seguintes.
8. **Ligação:** definiu a pergunta central (Q1), medida no full (M3).

## M3: Censo full: o fenômeno existe em escala (e se concentra na change ativa)

1. **Pergunta:** quantos são "done but missing", e *onde* o gap se concentra?
2. **Dado:** `openspec_code_refs` com filtro `task_done=1 AND anchor_sha IS NOT NULL`, colunas `exists_at_anchor` e `artifact_path`.
3. **Código:** SQL via DuckDB + `classify_spec_role()` (deriva o papel de ciclo de vida do diretório do `tasks.md`); gráfico `chart_census.png`.
4. **Resultado:** **N = 332.168** referências de tarefas marcadas concluídas **com** commit-âncora resolvido (as **8.746** concluídas **sem** âncora ficam fora e são reportadas no M4); **34.227** têm código ausente (`exists_at_anchor=0`), uma **taxa global de 10,3%** (297.822 presentes + 119 ambíguas completam o total). Essa taxa global se decompõe em **taxas por grupo, cada uma sobre o próprio denominador** (não sobre os 10,3%): **17,7% em `change_proposal`** (ausentes em change_proposal ÷ concluídas em change_proposal sendo 9.062 de 51.174) e **9,0% em `archived`** (ausentes em archived ÷ concluídas em archived sendo, 25.159 de 280.869). Há um resíduo de 125 refs `non-openspec` (6 ausentes = 4,8%); `living` e `na` têm zero refs.

   | Grupo | Total (n) | Código ausente | Taxa de ausência | % dos ausentes |
   |---|---|---:|---:|---:|
   | Total (concluídas c/ âncora) | 332.168 | 34.227 | 10,3% | 100% |
   | `change_proposal` (change ativa) | 51.174 | 9.062 | 17,7% | 26,5% |
   | `archived` (change arquivada) | 280.869 | 25.159 | 9,0% | 73,5% |
   | `non-openspec` (residual) | 125 | 6 | 4,8% | 0,0% |
   | `living` / `na` | 0 | 0 | - | - |

    *Total (332.168) = 34.227 ausentes (10,3%) + 297.822 presentes (89,7%) + 119 ambíguas (0,04%).*

5. **Análise e Interpretação:** O M3 dá o primeiro número de escala do estudo (34.227 referências, 10,3%), mas o número sozinho é cego: ele não diz *onde* o gap mora. Para ver isso, precisávamos de uma variável que o dataset não entrega pronta: o `spec_role`, o papel de ciclo de vida de cada spec. A derivação é a primeira lição. Tentar juntar com `spec_files` para pegar o papel **falha silenciosamente** (aquela tabela só guarda `spec.md`, nunca o `tasks.md` que a referência aponta), então o `spec_role` não pode vir de uma junção; ele é uma **função pura do diretório** no `artifact_path` (`changes/archive/` = change arquivada, `changes/<nome>/` = change ativa, `specs/` = viva). Derivar de onde o arquivo *vive* (em vez de procurar uma coluna) é o que torna o achado possível. O resultado reordena a intuição. A hipótese natural ("o gap está nas specs aposentadas, nos projetos abandonados") **não se sustenta**: a taxa das arquivadas é **9,0%**, *abaixo* da média de 10,3%. O gap não mora no arquivo morto; mora na **change ativa**, com **17,7%**, quase o dobro da taxa das arquivadas. Mas essa é a leitura por *taxa*; por *composição*, o quadro é outro: como `archived` é um grupo muito maior (280.869 vs 51.174), a maioria absoluta dos 34.227 ausentes (**73,5%**, ou 25.159) vive nas arquivadas, e só **26,5%** (9.062) nas ativas: as duas leituras são complementares, não contraditórias. A explicação está na semântica do workflow OpenSpec. Uma **change ativa** (`change_proposal`) é um documento que vem **antes** do código: o `tasks.md` é a lista de tarefas, e marcar uma caixinha **não** é afirmar "o código já existe e está commitado": é registrar uma **intenção**. O autor (ou o agente de IA, com o autor) tica a tarefa conforme *planeja* a mudança, como quem risca um item da lista do que a proposta vai fazer. Por isso a checkbox pode estar marcada (`task_done=1`) enquanto o código que ela aponta não está no commit de referência (`exists_at_anchor=0`): o "done" do documento é uma **declaração de intenção**, não uma **certificação de que o código existe**: são duas coisas diferentes, que podem não coincidir. E há um detalhe que fecha o quadro: `living` tem **zero** refs, porque o `tasks.md` só existe sob `openspec/changes/`, nunca sob `openspec/specs/`. Ou seja, todo o fenômeno "done but missing" é uma propriedade do **workflow de change ativa** do OpenSpec, não das specs vivas nem de "projetos abandonados". Duas cautelas para não ler o número errado. Primeiro, a "taxa de missing" (10,3% global, ou 17,7%/9,0% por grupo) **não é** a "taxa de never": ela mede `exists_at_anchor=0` (o código não está no commit de referência), e não diz se ele *nunca* foi escrito, foi removido, ou chegou depois; essa separação é a clonagem + classificação (M8). Segundo, a ideia de "lag" (o código chegar *depois*) é uma *interpretação* que o M3 ainda não sustenta: afirmar que o código "vai chegar" exigiria clonar o subset change_proposal e classificar cada ref: fica como hipótese a testar, não como conclusão. O que o M3 permite afirmar com segurança é mais modesto e já é um achado: **o papel importa**, e a lacuna se concentra nas changes ativas (17,7% vs 9,0%): não é mais uma hipótese não testada, é um resultado do censo.
6. **Decisão:** denominador = refs concluídas **com** `anchor_sha`; os `NULL` (âncora ausente) são reportados à parte. `spec_role` é derivado do caminho (não de uma coluna de junção), porque `spec_files` só guarda `spec.md`: o `tasks.md` apontado pela ref vive só em `openspec/changes/`, e o papel é uma função pura do diretório.
7. **Significado:** o "concluída sem código" não é marginal: é fenômeno de escala; e ele é uma propriedade do **workflow de change ativa** do OpenSpec, não de "projetos abandonados" (o gap é *menor* nas changes arquivadas, 9,0%, e *maior* nas changes ativas, 17,7%).
8. **Ligação:** antes de classificar, precisávamos entender a coluna `exists_at_anchor` (M4).

## M4: Descoberta: `exists_at_anchor` não é binário

1. **Pergunta:** a coluna é realmente 0/1?
2. **Dado:** `openspec_code_refs`, coluna `exists_at_anchor`.
3. **Código:** SQL `GROUP BY exists_at_anchor`.
4. **Resultado:** `0` (51.979), `1` (361.083), `2` (130, em 5 repos), `NULL` (22.209), e **`NULL` ⟺ `anchor_sha=NULL`** (correlação perfeita). Das 22.209 com âncora nula, **8.746 têm `task_done=1`** (as concluídas sem âncora, excluídas do denominador do M3). E os **51.979** com `exists_at_anchor=0` contam **todas** as refs (sem filtrar `task_done`); o censo do M3 (**34.227**) restringe a `task_done=1`. A diferença de **17.752** são refs com código ausente mas **não** marcadas como concluídas.
5. **Análise e Interpretação:** O M4 parece uma formalidade (um simples `GROUP BY`), mas é o guardrail que sustenta o número do M3. A lógica é: o 10,3% foi calculado como `exists_at_anchor=0` sobre as refs concluídas com âncora, e essa conta **assume** que a coluna é binária (0 ou 1). Confiar num headline sem antes verificar o tipo da coluna é a receita clássica para um erro silencioso, então, antes de seguir, paramos para olhar a coluna inteira, sem o filtro do M3. O que apareceu são **quatro** valores, não dois: `1` presente (361.083), `0` ausente (51.979), `2` ambíguo (130) e `NULL` (22.209). E cada valor escondido conta uma história. O `NULL` é o mais revelador: os 22.209 casos **coincidem exatamente** com os que têm `anchor_sha` nulo: correlação perfeita. Isso muda o significado: o `NULL` não é "dado faltando" no sentido preguiçoso de uma planilha mal preenchida; é um valor **determinístico**: sem commit de referência resolvível, a pergunta "o código existe no âncora?" **não tem resposta**, e o `NULL` é a resposta honesta. O `2` (ambíguo) é outro sinal: 130 refs em apenas 5 repos, um deles concentrando 100: o caso raro em que a existência não dá para decidir. A consequência prática fecha o círculo com o M3: o denominador do 10,3% usou `anchor_sha IS NOT NULL`, então ele **já excluía** os 22.209 `NULL`: o headline está seguro. Mas só sabemos que ele está seguro *porque* olhamos: sem esta checagem, alguém poderia somar os `NULL` como "ausentes" (inflando o gap) ou ignorá-los (distorcendo o denominador). O M4 é, portanto, uma **contribuição de qualidade de dados**: o `DATA_DICTIONARY` descreve a coluna como binária ("1 se existia"), e documentar que ela é, na verdade, `0/1/2/NULL` (com `NULL ⟺ anchor_sha NULL`) é uma correção que todo usuário futuro do SpecMine herda.
6. **Decisão:** documentar como **contribuição de qualidade de dados**; tratar `NULL` separadamente (não somar).
7. **Significado:** a coluna é sub-documentada no `DATA_DICTIONARY`; sem essa descoberta, qualquer headline estaria errado.
8. **Ligação:** permitiu medir o 10,3% com segurança e partir para a taxonomia.

## M5: Taxonomia: arquivo real ou ruído de path?

1. **Pergunta:** dos 34.227, quantos são arquivo de verdade e quantos são ruído?
2. **Dado:** `openspec_code_refs`, filtro do M3, coluna `code_path`.
3. **Código:** `taxonomy.py` → `classify_path()` pela *forma* do path: `relative_ext` (diretório + extensão), `bare_ext` (só nome + extensão), `non_file` (glob / absoluto / sem extensão); gráfico `chart_taxonomy.png`.
4. **Resultado:** das 34.227 refs, `relative_ext` 17.799 · `bare_ext` 13.326 · `non_file` 3.102 → **91% arquivo real (31.125 de 34.227), 9% ruído**.
5. **Análise e Interpretação:** O M5 responde à objeção mais natural contra o número do M3: "e se esses 34.227 'ausentes' forem, na verdade, caminhos mal escritos (ruído), e não arquivos que realmente faltam?" Vale fixar, primeiro, de onde `code_path` vem: é o caminho de código que a própria spec **nomeia**: a task do `tasks.md` cita o arquivo que deveria implementá-la, e o dataset parseou essa referência do texto do `tasks.md` ("code path named by a task", no `DATA_DICTIONARY`). Ele **não** vem de um commit nem de uma tabela separada de refs; o commit (`anchor_sha`) só entra *depois*, para verificar se aquele caminho existe na árvore naquele commit (`exists_at_anchor`). Ou seja, `code_path` é a **alegação da spec** sobre onde o código deveria estar, e o M5 julga se essa alegação é um arquivo de verdade ou ruído. Para responder sem achismo, classificamos o `code_path` pela **forma** do caminho. A decisão central é por que **três níveis, e não dois**. A tentação é separar só "arquivo vs não-arquivo", mas isso esconde uma ambiguidade importante. Um path como `src/foo.ts` (diretório + extensão) aponta para um lugar **exato**: dá para procurar e verificar. Um path como `foo.ts` (só nome + extensão) é claramente um arquivo real, mas **não diz onde** ele deveria estar; não dá para um lookup direto. E há o terceiro caso, `non_file`: glob (`*.ts`), caminho absoluto ou sem extensão, que nem sequer identifica um arquivo. Agrupar os dois primeiros como "arquivo" esconderia que `bare_ext` é um meio-termo: é arquivo de verdade, mas **inutilizável para verificação**. Os números desfazem a objeção do "ruído": `relative_ext` 17.799 + `bare_ext` 13.326 = **31.125 (91%)** são arquivos reais; só **3.102 (9%)** são `non_file`. Ou seja, o "done but missing" **não é** path malformado: é arquivo que deveria existir e não existe. O guardrail é consequência direta dessa tripartição: **nunca somar** os 9% de `non_file` com o "missing real": são naturezas diferentes ("não dá nem para interpretar o caminho" vs "o caminho é válido mas o arquivo não existe"), e misturá-las contaminaria qualquer taxa. A tripartição ainda decide o passo seguinte: só os 17.799 `relative_ext` (localizáveis) formam a população da clonagem + classificação, porque são os únicos que o `git` consegue resolver para separar "nunca escrito", "escrito e removido" e "criado depois".
6. **Decisão:** por que **3 níveis**, não 2? Porque `bare_ext` é ambíguo (não diz *onde* o arquivo deveria estar), diferente de `relative_ext` (lookup direto). Guardrail: **nunca somar** `non_file` com o "missing real".
7. **Significado:** o "done but missing" **não é** path malformado: é arquivo que deveria existir e não existe.
8. **Ligação:** os 17.799 `relative_ext` viram a população da clonagem + classificação.

## M6: Acessibilidade: o que as specs pedem?

1. **Pergunta:** quais preocupações de acessibilidade aparecem, e em que proporção são verificáveis?
2. **Dado:** `specs.jsonl` (470.795 specs, texto bruto) + `spec_content_features` (contexto).
3. **Código:** `extract_accessibility.py`: streaming + vocabulário (`WCAG`, `Section 508`, `ADA`, `a11y`, `screen reader`, `alt text`, `ARIA`, `keyboard`, `contrast ratio`, etc.) + regra de **verificável por linha**; gráfico `chart_accessibility.png`.
4. **Resultado:** **97.883** linhas de requisito em 10.717 repos; **27,1% dessas linhas são verificáveis**; openspec 37,0% vs docs_embedded 8,9%.
5. **Análise e Interpretação:** O M6 responde à Q2 (a pergunta secundária que sobrou do pivô do M2), mas não do jeito óbvio. Não estamos contando *quantas* specs falam de acessibilidade; estamos perguntando *quão testável* é o que elas pedem. Para chegar a isso, varremos o **corpus inteiro** de specs (o `specs.jsonl`, com 470.795 specs) **linha a linha**, em streaming, procurando um vocabulário de acessibilidade (WCAG, Section 508, leitor de tela, alt text, ARIA, navegação por teclado, contraste, e afins), definido em `ACCESSIBILITY_PATTERNS` no `extract_accessibility.py`. Cada linha do corpus que menciona um desses termos vira uma "linha de requisito de acessibilidade": foram **97.883** delas, espalhadas por 10.717 repos. Sobre essas linhas, aplicamos o critério de **verificável**: uma **regra reprodutível, não um julgamento de gosto**, implementada em `IMPERATIVE` (`shall`/`must`) e `THRESHOLD` (limiar mensurável) no `extract_accessibility.py`: uma linha é verificável se contém `shall`/`must` **ou** um limiar mensurável (uma razão como 4,5:1, uma comparação seguida de número, um nível WCAG AA/AAA, ou um número com unidade). A distinção que importa, então, é entre requisito **verificável** e **vago**: "o app deve ser acessível" não passa no critério; não dá para testar; "o contraste deve ser de pelo menos 4,5:1" passa: dá para medir. E o critério é aplicado **por linha**, não por spec: uma spec é um documento inteiro, e medir "a spec é verificável?" esconderia que dentro dela há uma linha testável e dez vagas. Contar linha a linha captura a proporção real. O resultado tem duas camadas. A primeira é o número geral: **27,1%** das 97.883 linhas são verificáveis, ou seja, quase três quartos do que as specs pedem de acessibilidade é vago. A segunda camada é o achado: a taxa **não é uniforme** entre ferramentas. Ferramentas formais (`openspec` (37,0%) e `speckit` (35,6%)) produzem requisitos de acessibilidade **muito mais** verificáveis do que specs soltas em documentação (`docs_embedded`, 8,9%). A diferença faz sentido: uma ferramenta formal impõe template e vocabulário de "shall/must" e limiares; uma spec embutida num README é texto livre, onde "acessibilidade" tende a aparecer como intenção, não como critério. As guardrails contam como chegamos a um número limpo: o termo `ADA` não pode ser buscado como sigla solta (colidiria com a linguagem Ada e com o token Cardano), e `caption`/`transcript` foram removidos por gerarem falsos-positivos. O M6, por fim, prepara o M8: é a presença de requisitos de acessibilidade (muitas vezes aspiracionais) que a ponte vai cruzar com a taxa de "nunca implementado".
6. **Decisão:** "verificável" é **por linha** (`shall`/`must` ou limiar mensurável), não por spec; `ADA` case-sensitive (evitar a linguagem Ada e o token Cardano); `caption`/`transcript` removidos (falsos-positivos).
7. **Significado:** ferramentas formais (openspec, speckit) produzem requisitos de acessibilidade **muito mais verificáveis**.
8. **Ligação:** alimenta a ponte acessibilidade × implementação (M8).

## M7: Calibração: quanto é normalização de path?

1. **Pergunta:** quanto do "missing" poderia ser só caminho escrito diferente?
2. **Dado:** `openspec_code_refs` com `exists_at_anchor=1` e `resolved_path` preenchido.
3. **Código:** comparação `resolved_path != code_path`.
4. **Resultado:** `relative_ext` resolve em path diferente em **15,2%**; `bare_ext` em 94,8% (mas isso é **tautológico**: nome solto sempre ganha diretório ao resolver).
5. **Análise e Interpretação:** O M7 é uma **calibração**, não uma contagem nova. Primeiro, um esclarecimento de vocabulário: "missing" aqui é o "done but missing" do M3: a ref cujo `exists_at_anchor=0`, ou seja, o arquivo que a task nomeou **não foi encontrado** no commit de referência. A objeção que o M7 responde é: "e se parte do 'missing' não for ausência real, mas o código existindo sob um caminho ligeiramente diferente: um arquivo renomeado, um diretório movido, um path normalizado?" Para calibrar isso, olhamos os refs que **deram certo** (`exists_at_anchor=1`) e que têm `resolved_path` preenchido. E aqui está a fonte da interpretação: `resolved_path` é a coluna que guarda o "matched tree path": o caminho **real** na árvore git onde o arquivo foi encontrado, quando foi (definição do `DATA_DICTIONARY`). Quando o dataset achou o arquivo, registrou *onde* achou; nos "missing", não há `resolved_path` para comparar. Medimos, então, com que frequência o `resolved_path` difere do `code_path` escrito. A lição aparece na diferença entre duas formas de path. Para `relative_ext` (diretório + extensão), a taxa de diferença é **15,2%**: é aí que a inferência de renomeação/normalização se apoia: o arquivo **foi encontrado** (`exists=1`), mas sob um caminho **diferente** do que a spec escreveu, a assinatura de um path escrito "fuzzy" (renomeado, movido ou normalizado), não de uma ausência. Para `bare_ext` (só nome + extensão), a taxa é **94,8%**, mas esse número é **tautológico**, não informativo: um nome solto como `foo.ts` não tem diretório, então *qualquer* resolução é obrigada a acrescentar um diretório (`src/foo.ts`), e `resolved_path != code_path` acontece quase sempre, por construção. Citar o 94,8% como se fosse renomeação seria um **erro de interpretação**: é a assinatura do artefato, não do fenômeno. O guardrail é consequência direta: **só o 15,2%** entra como sinal de renomeação/normalização. Isso calibra a clonagem + classificação: quando o M8 for classificar os "missing" em never/deleted/created_later/renamed, ele sabe que precisa de uma camada de detecção de rename (`git log --follow`), porque ~15% dos caminhos escritos não batem exato com onde o código está, mesmo quando ele existe.
6. **Decisão:** usar **15,2%** como sinal de renomeação/normalização; **não** citar o 94,8% (seria um erro de interpretação).
7. **Significado:** motiva a camada de renames/temporal da clonagem + classificação.
8. **Ligação:** define o que a clonagem + classificação precisa recuperar.

## M8: clonagem + classificação + Ponte: quantos são de fato "never"?

1. **Pergunta:** dos "done but missing", quantos são *nunca implementados* (vs. renomeados ou implementados depois)?
2. **Dado:** `taxonomy_e0.csv` (17.799 `relative_ext`) + `spec_files` (estrelas/linguagem) + `git clone` dos repos.
3. **Código:** `clone_classify.py`: `classify_ref()` com 5 buckets, `ALL_BRANCHES=True`, `git log --diff-filter=A` / `--follow`; gráficos `chart_outcomes.png` + `chart_by_bucket.png` + `chart_bridge.png` + `chart_bridge_repo.png`.
4. **Resultado:** (amostra M8: 137 repositórios clonados com sucesso e 1.298 referências classificadas) **never 54,5%** (mediana **geral** por repo 66,7%) · deleted_before_anchor 29,5% · created_later 9,2% · renamed 4,1% · other 2,7% · alternative_path 0%. **Inversão por maturidade** (0–9: deleted 46% > never 41%; 10+: never ~57–59%). **Ponte (acessibilidade):** proporção agregada por referência de `never`: 60,4% (com acessibilidade) vs 41,5% (sem); mediana por repositório **em cada grupo de acessibilidade**: 70,7% vs 50,0%: medidas complementares (a proporção agregada atribui maior peso aos repositórios com mais referências; a mediana dá o mesmo peso a cada repositório), persistindo em todos os buckets.
5. **Análise e Interpretação:** O M8 é onde o estudo responde à pergunta que o dataset não podia responder. Todo o caminho até aqui (o 10,3% (M3), os 91% arquivos reais (M5)) descreve *o quê*: tarefas marcadas como concluídas sem código no âncora. Mas o parquet só diz `exists_at_anchor=0`; ele **não diz por quê**. Para separar "nunca foi escrito" de "foi escrito e removido" de "foi escrito depois" de "foi renomeado", não há outro caminho senão ir ao histórico: tentamos clonar os 152 repositórios selecionados pela amostragem. A clonagem foi bem-sucedida em 137 deles, nos quais analisamos o histórico Git (`--diff-filter=A` / `--follow`) e classificamos 1.298 referências. É a **única** etapa do estudo que não é uma leitura do parquet, e as escolhas aqui têm motivação: `ALL_BRANCHES=True` para que "never" signifique *nunca em nenhuma branch* (conservador: uma feature branch não-mergeada conta como "implementado"); `git clone` em vez de API (sem rate limit, e `--follow` detecta rename); e uma amostragem por repositório, estratificada. Cada estrato é a combinação de uma faixa de estrelas (0–9, 10–99, 100+) com uma linguagem. A cota de cada faixa foi fixada por desenho (50, 45 e 57 repositórios, total 152), de modo deliberadamente desproporcional: a faixa 100+ entra inteira (censo de 57 repositórios), a 10–99 com 45 de 147 (≈30,6%) e a 0–9 com 50 de 2.332 (≈2,1%). Dentro de cada faixa, a cota é repartida entre as linguagens em proporção ao número de repositórios de cada uma, pelo método do maior resto (largest-remainder), para que a soma feche exatamente. Dentro de cada estrato, os repositórios são sorteados ao acaso, sem reposição (DataFrame.sample, random_state=SEED). A semente fixa torna o sorteio reproduzível (o mesmo quadro de dados gera sempre os mesmos 152 repositórios), mas não o torna determinístico por regra: é um sorteio pseudoaleatório. Antes dos números, uma nota sobre a fonte deles: os valores globais (54,5% never, 29,5% deleted_before_anchor, 9,2% created_later) vêm da **distribuição impressa pelo script** (`m8_bridge.py` lê `classification_results.csv` e imprime `value_counts()`), e agora também estão no gráfico **`chart_outcomes.png`**. Os outros dois gráficos trazem recortes: `chart_by_bucket.png`, a composição **por bucket** (a inversão), e `chart_bridge.png`, a **ponte** acessibilidade. Os percentuais por bucket (como o 46% vs 41%) saem do `crosstab` do mesmo script. O resultado tem uma leitura principal e duas secundárias. A principal: **54,5% never + 29,5% deleted_before_anchor = 84% genuinamente ausentes**: o "done but missing" é, na esmagadora maioria, código que nunca existiu ou que foi removido, não um erro de medição. E aqui se **fecha o laço com o M3**: o M3 deixou em aberto "será que é *lag* (o código chega depois)?"; na amostra M8, `created_later` correspondeu a 9,2% das referências classificadas: a chegada posterior do código não foi a explicação predominante, mas essa proporção não deve ser extrapolada para toda a população sem considerar o desenho amostral. Antes de interpretar a inversão, um esclarecimento: "maturidade" aqui é um **proxy**: a **contagem de estrelas** do repositório (`repo_stars`, de `spec_files.parquet`), fatiada em três faixas (`0–9`, `10–99`, `100+`) no `clone_classify.py`. Estrelas medem popularidade, não maturidade de engenharia; a usamos como sinal aproximado de "repo sério vs. experimento", cientes de que é uma convenção, não uma medida direta. A primeira leitura secundária é a **inversão com maturidade**: em repos 0–9 estrelas, `deleted_before_anchor` (46%) supera `never` (41%): é *churn*, código que aparece e some; em repos 10+ estrelas, `never` domina (~57–59%): é *não-implementação*, intenção que nunca virou código. A segunda é a **ponte com a acessibilidade** (M6): repos com requisitos de acessibilidade têm **60,4% never vs 41,5%** nos sem, e a diferença persiste em todos os buckets de estrelas. Esse padrão é compatível com a hipótese de que parte dos requisitos de acessibilidade declarados nas specs não se converte em implementação. Entretanto, essa interpretação permanece exploratória: a comparação no nível de repositório não forneceu evidência estatística suficiente para rejeitar a hipótese nula (p = 0,169), e o teste não incorpora uma correção pelo desenho amostral. Duas ressalvas para não ler errado. Primeiro, a ponte **não é uma regressão**: é `pd.crosstab` + `.mean()`, uma comparação descritiva de proporções (sem reta, sem resíduos, sem coeficientes). Hipótese e checagem inferencial. A interpretação dos resultados de M6 sugere uma possível tensão entre a declaração de requisitos de acessibilidade nas especificações e sua efetiva implementação. Essa observação motiva a hipótese exploratória de que repositórios cujas especificações declaram requisitos de acessibilidade apresentam uma proporção maior de referências classificadas como `never`. Formalmente, H0 estabelece que a distribuição das taxas `never` por repositório é igual entre os grupos com e sem requisitos de acessibilidade; H1 estabelece que as distribuições são diferentes entre os dois grupos. O gráfico `chart_bridge_repo.png` apresenta a pista descritiva que fundamenta essa investigação: a mediana da taxa `never` foi de 70,7% nos repositórios com acessibilidade e 50,0% nos repositórios sem acessibilidade. Note que essas medianas diferem da proporção agregada por referência citada no campo 4 (60,4% vs 41,5%): a proporção agregada pesa mais os repositórios com mais referências, enquanto a mediana dá o mesmo peso a cada repositório: são duas medidas complementares, não contraditórias. A comparação foi realizada no nível de repositório, evitando tratar referências pertencentes ao mesmo repositório como observações independentes. Foi utilizado o teste Mann–Whitney U bilateral, que não forneceu evidência suficiente para rejeitar H0 ao nível de significância de 5% (p = 0,169). Esse resultado deve ser interpretado com cautela. A amostra M8 foi obtida por amostragem estratificada desproporcional por estrelas e linguagem, e 15 repositórios selecionados não puderam ser clonados. O teste apresentado não incorpora, portanto, uma correção pelo desenho amostral. A diferença observada permanece como evidência descritiva de uma possível associação, não como uma relação populacional estatisticamente estabelecida. Por fim, uma limitação documentada: `classification_results.csv` guarda a **classificação**, não os SHAs que a produziram: decisão de não enriquecer o artefato.
6. **Decisão:** amostragem estratificada (faixa de estrelas × linguagem), probabilística e reproduzível: cotas fixas por faixa (50 / 45 / 57; 100+ como censo), repartidas entre linguagens pelo maior resto, com sorteio aleatório sem reposição dentro de cada estrato (random_state=SEED); `ALL_BRANCHES=True` (conservador); `git clone` em vez de API (único passo não-determinístico: git é mutável); 5 buckets; reportar **refs e repos** (aninhamento).
7. **Significado:** 84% são classificados como `never` ou `deleted_before_anchor`; a composição dos resultados varia descritivamente entre os buckets de estrelas. A ponte com acessibilidade apresenta diferenças descritivas entre os grupos, mas não estabelece uma relação populacional estatisticamente significativa.
8. **Ligação:** é o resultado central do paper.

**Leitura em três níveis (M8).** O estudo distingue três coisas: (1) o que foi **medido no censo**: M3 a M7, sobre a população completa (10,3% de missing, 91% arquivos reais, 27,1% verificáveis); (2) o que foi **observado na amostra**: M8, sobre os 137 repositórios amostrados (54,5% never, medianas 70,7% vs 50,0%); e (3) o que **permanece como hipótese**: a associação acessibilidade × não-implementação, que o Mann–Whitney U não estabeleceu como relação populacional (p = 0,169). Próximo passo: se o estudo precisar generalizar para a população de repositórios, o avanço não é adicionar testes por adicionar: é incorporar os pesos de inclusão dos estratos definidos pela combinação de faixa de estrelas e linguagem (considerando a alocação desproporcional, especialmente a maior fração de seleção nas faixas de 10–99 e 100+ estrelas) e avaliar o possível viés decorrente das 15 falhas de clonagem. Como a seleção é probabilística, a probabilidade de inclusão de cada repositório é conhecida (aproximadamente 2,1% na faixa 0–9, 30,6% na 10–99 e 100% na 100+), o que viabiliza ponderar pelo inverso dessa probabilidade.

## Glossário

| Termo | Definição exata |
|---|---|
| `done but missing` | ref com `task_done=1`, `anchor_sha` não-nulo e `exists_at_anchor=0` |
| `exists_at_anchor` | 0 (ausente), 1 (presente), 2 (ambíguo), NULL (âncora ausente ⟺ `anchor_sha` NULL) |
| `anchor_sha` | commit contra o qual o tree foi resolvido |
| `code_path` | caminho de código citado pela task no `tasks.md` |
| `relative_ext` | caminho relativo com diretório e extensão (`src/foo.ts`) |
| `bare_ext` | só nome + extensão (`foo.ts`), sem diretório |
| `non_file` | glob / absoluto / sem extensão |
| `verifiable` | linha com `shall`/`must` **ou** limiar mensurável (razão, AA/AAA, comparador, número+unidade) |
| `never` | arquivo nunca commitado em nenhuma branch (`ALL_BRANCHES=True`) |
| `deleted_before_anchor` | arquivo escrito e removido antes do âncora |
| `created_later` | arquivo commitado depois do âncora |
| `renamed` | arquivo existe sob outro nome (via `--follow`) |
| `alternative_path` | mesmo basename em outro caminho (0 casos) |
| `other` | âncora ausente no clone (force-push) ou ambíguo (adicionado antes do âncora sem deleção/renomeação detectada) |
| `spec_role` | papel de ciclo de vida da spec, função pura do diretório do `tasks.md` (`changes/archive/` = `archived`, `changes/` = `change_proposal`, `specs/` = `living`) |
| `change_proposal` | mudança ativa (`changes/<nome>/`): taxa de missing 17,7% |
| `archived` | mudança concluída/arquivada (`changes/archive/`): taxa de missing 9,0% |
| `living` | spec atual (`specs/`): sem `tasks.md`, zero refs |
| `taxa de missing` | `exists_at_anchor=0 ÷ refs concluídas com âncora` (M3, 10,3%); ≠ `taxa de never` (M8) |
